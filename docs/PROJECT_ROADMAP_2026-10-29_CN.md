# UPay 项目梳理、工程经验与优化路线图

审查基准：2026-10-29 的本地源码、操作入口和测试。本文区分现有实现与未来规划；不是线上资源审计、财务审计或已授权实施的任务单。返回[项目总览](../README.md)。

## 1. 项目定位与现有能力

当前是一套服务 UPB / UPW 的运营数据平台，负责后台文件采集、数据处理、测试验收、正式发布和经营分析。它已经包含服务端 BD 数据隔离、主管理员导出权限、环境隔离、输出哈希验收与已发布快照读取。

链路：`后台 → 下载/暂存 → 本地原始数据 → 关系与规则匹配 → 每日/月度汇总 → 测试验收 → 正式发布 → 网站`。

| 层次 | 现有实现 | 尚缺的能力 |
| --- | --- | --- |
| 接入 | UPB 自动补齐和分段；UPW 现有 Chrome 扩展与本地导入 | 统一调度、完整任务台账、长期现场稳定性验收 |
| 处理 | 状态/日期/行数校验、去重、归属、汇率和聚合 | 独立金额对账、历史差异处理、明确零数据日 |
| 发布 | 测试与正式隔离、代码摘要和输出哈希、读回核验 | 跨云端组件的批次版本管理、完整回滚 |
| 展示 | 趋势、目标、排名、贡献、活跃度、代理资料 | 客户运营任务闭环、漏斗与留存 |
| 管理 | 主管理员、其他管理员、BD | 运营/财务/审核职责、团队协作与审计 |

业务数据仍依赖本机原始文件及私密配置；克隆仓库不能单独恢复生产运行。`db/schema.ts` 目前为空，不能把脚手架当作已部署业务数据库。

## 2. 近期实现与学到的知识点

### 下载必须验证业务状态

页面出现导出按钮、日期输入框出现目标日期，都不足以证明查询成功。UPW 的范围控件可能只更新输入显示，尚未更新实际查询模型；需要提交控件，并用结果日期和状态检查。切换标签页还可能继承旧筛选，应重置并只在目标可见页查找按钮、表格与总数。

UPB 的不同渠道也有独立日期字段、主/子订单和导出上限。不能统一按一个字段或一个页面选择器处理。导出超限应拆分范围，核对行数与订单；不能把一次成功下载等同于完整数据。

参考：[Playwright 条件等待](https://playwright.dev/docs/actionability)。框架的可操作性检查解决控件状态，业务范围仍由项目校验。

### 恢复、幂等与文件归档

近期已实现 UPB 完成日期哈希核对、UPW 完整阶段/日期断点保存、页面刷新上限及原始数据安装失败回退。计数不变本身不是卡死证据，校验错误和明确零数据不能盲目刷新绕过。

尚需建设按批次保存的不可变原始导出归档。Downloads 中的文件可能被修改，未来应保存下载文件哈希、查询条件、条数、任务号和导入结果。未完成日期的部分分段仍可能重新下载；当前并非逐分段精确一次执行。

### 日期有多种含义

- UPB 后台按 UTC+0 日切，UPW 后台按 UTC+8 日切。
- 文件下载时间、清单生成时间、业务日期不是同一概念。
- 已下载、已校验、已导入、测试已验收和正式已发布必须分别记录。
- 历史文件含某日期，只能证明出现过该日期，不能独立证明完整性。

UPW 日期清单在本地安装时一起更新；任何一份索引写入失败应回退，不应先宣布成功再扫描历史生成索引。

### 代理关系增量需要证据

保留历史底表，按用户 UID 合并增量。导出最新分段应满足必需字段、行数、时间倒序、历史 UID 重叠和覆盖范围；不能为了通过校验把筛选后的总数改大。当前仍由用户指定关系段数，缺少足够重叠时停止；后续应自动确定足够的分段，并强化连续性证明。

### 规则与来源需要版本

UPB 同文件重复订单按最早申请记录保留，时间相同或缺失时保留首个源行；跨文件按较新账期/版本选择快照。此规则已进入代码和测试，但不是所有业务场景下通用的去重真理。规则变更要说明影响日期、保留来源、测试重算和验收，不无痕修改历史。

## 3. 第一优先级：数据可靠与日常体验

| 改进 | 交付内容 | 验收标准 |
| --- | --- | --- |
| 统一操作台 | 每个平台显示已下载、已导入、测试通过、正式发布的截止日和下一步 | 不需要用户记忆多个文件夹与脚本顺序 |
| 每日数据台账 | 平台 × 数据类型 × 业务日；查询条件、文件哈希、行数、金额、状态、错误、批次 | 能回答某日为什么缺失，零数据与缺文件明确区分 |
| 批次归档 | 原始导出固定保存；校验前后核对哈希；避免长期引用可修改的下载文件 | 原始数据可追溯，文件变化不会静默进入计算 |
| 独立对账 | 后台汇总→文件→计算结果→云端→网站，缺渠道和归属异常单独呈现 | 关键差异阻断发布，不能只验证同一计算结果的往返一致性 |
| 历史修正 | 可配置近期回查窗口、订单状态与退款差异、重算范围、月结后调整 | 迟到交易不会因日期已覆盖而永久遗漏；重复导入不重复计数 |
| 发布与回退 | 新批次写入并验收后切换当前版本；保留上一完整版本 | 中途失败不会让读者读到半个批次；可恢复指定版本 |
| CI 与交付 | 统一测试入口、版本记录、桌面副本来源、文档同步 | Python、前端/权限、扩展测试都被执行；发布来源明确 |
| 备份恢复 | 源文件、规则、关系表、必要私密配置的受控备份和负责人清单 | 用另一台机器恢复测试流程，记录恢复时长与缺失项 |

Google Sheets API 支持同一个 batchUpdate 中子请求原子应用，但不自动覆盖 Apps Script 计算和 Worker KV。短期可保留现有存储，逐步增加批次版本切换。[官方说明](https://developers.google.com/workspace/sheets/api/guides/batch)

## 4. 第二优先级：从看业绩到推动业务

区分合作客户（代理商、API 商户、渠道伙伴）与终端用户。两者需要关联，但生命周期、权限、联系人和指标不同。UPB/UPW 跨平台身份也需明确映射，不能仅凭相同名称合并。

| 业务模块 | 实际用途 | 必需条件 |
| --- | --- | --- |
| 合作客户档案 | 联系人、BD、合作模式、合同、目标、平台映射、历史业绩集中查看 | 稳定客户 ID、字段所有者与维护权限 |
| 生命周期与跟进 | 从接洽、合作、起量、稳定、衰退到暂停/恢复；待办有责任人和截止时间 | 状态与事件定义、任务记录、关闭原因 |
| 客户预警 | 消费下滑、目标落后、新合作未起量、长期未跟进、集中度风险 | 可配置阈值，先排除数据缺失、退款和季节性 |
| BD 工作台 | 今日待联系、重点客户、商机、风险客户、跟进效果 | 服务端数据范围和任务权限 |

优先闭环：消费下降 → 展示变化依据 → 分配 BD → 记录原因与行动 → 设置复查时间 → 验证数据是否恢复。预警不应只展示红色数字，也不应在未授权时自动向客户发消息。

## 5. 第三优先级：深入分析和更多场景

| 模块 | 可支持的场景 | 数据与规则前提 |
| --- | --- | --- |
| 用户漏斗 | 注册→KYC→申请→成功开卡→激活→首笔消费 | 用户级阶段事件和时间；不能将不同日期的汇总数直接相除 |
| 留存与召回 | 有卡无消费、新用户持续消费、曾消费后沉默 | 用户与交易历史、批次人群定义、退款与有效消费口径 |
| API 商户接入 | 接洽、KYB、合同、技术测试、上线、首笔交易与起量 | 客户负责人、接入里程碑、技术事项和受控资料 |
| 返佣与月结 | 规则试算、复核、对账单、历史调整、付款状态 | 规则生效日期、币种/汇率、结算依据、月结冻结与审计 |
| 收益分析 | 客户/渠道的收入、成本、返佣和毛利 | 手续费、渠道成本和合同规则；交易量不能代替利润 |
| 活动与渠道 | 邀请码/活动带来的开卡、首笔消费、留存与收益 | 活动标识、成本、归因窗口及跨平台映射 |
| KYB 管理 | 材料、补件、审核、到期复核 | 私有附件、细分权限、审批日志；单独规划上线 |

这些均为建议，尚未上线。现有代理活跃度是基于历史正消费的规则指标，不等于完整终端用户留存或客户流失模型。

## 6. 数据模型与架构演进

1. 建立稳定的客户 ID、BD ID、平台 UID/名称映射。改名和转交 BD 不应生成无关的新客户。
2. 归属、合作模式、目标与返佣规则保存生效起止时间及版本，分别支持“当时归属”和“当前负责人”视角。
3. 保存合作开始、开卡、首笔消费、暂停、恢复、转交等事件时间，为周期和转化分析提供依据。
4. 保留接入、处理、业务管理、展示四层。多人在线写入时，为客户、任务与规则引入事务数据库；附件采用私有存储，汇总看板继续复用。
5. 按运营、财务、审核、BD、团队主管划分职责；新接口服务端逐次检查权限，默认拒绝。参考 [OWASP 授权建议](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

不建议同时重做网站、迁移全部历史交易、引入完整 KYB 和财务结算。先确定数据、负责人、指标和验收标准，再选择存储与运行产品。

## 7. 实施顺序与完成定义

| 阶段 | 重点 | 完成定义 |
| --- | --- | --- |
| 1 | 统一操作台、台账、归档、恢复、对账和交付 | 连续多个工作日无需手改文件；中断可续跑，重试不重复入账，恢复经过演练 |
| 2 | 客户档案、稳定 ID、预警、跟进与 BD 工作台 | 重点客户变化都有责任人、处理记录和复查结果 |
| 3 | 漏斗、留存、API 接入、返佣和收益 | 明细数据充分，指标可追溯，业务规则有版本，结算可复核 |
| 4 | 在线配置、细分权限、审计、按需迁移 | 多人操作可控，新人能接手，新设备可恢复 |

建议下一批范围：统一操作台、每日数据台账、下载文件归档、客户档案和带责任人的预警。当前文档不承诺完成日期或投入规模，具体排期需在功能范围和数据可得性确认后估算。

## 8. 开发与验收边界

`npm run check:pipeline` 包含 Python 测试、Apps Script 生成物同源检查、Node `.mjs` 与扩展 `.cjs` 测试；另运行 `npx tsc --noEmit` 和测试站构建。新增流程需覆盖残留筛选、旧查询结果、慢查询、会话失效、超限分段、断点恢复和文件变化。

这些检查不访问真实后台，也不能证明生产数据完整。真实验收需留存经脱敏的操作记录和文件/金额核对结果。源码推送不会更新扩展的本机运行实例、后台数据、Google 接口或网站部署。
