# UPay 看板项目检查与优化建议

检查日期：2026-09-24。范围：当前工作区的前端、筛选/汇总计算、Worker API、Apps Script、UPW/UPB 本地计算及同步程序、环境配置、文档和测试入口。属于代码审查与有限验证，不代表已完成生产压测、安全渗透或逐笔财务核对。正式数据由独立 Desktop 启动器运行；已对照其 UPB `build_business_history.py` 与仓库脚本，内容一致；本轮没有实际运行生产同步。

2026-09-25 跟进：正式 Apps Script / Worker 已发布；正式与测试站均核对到 `2026-09-24`。UPW、UPB 当前正式每日汇总与临时重算结果逐字节一致，没有重传生产数据。生产 UPW 启动器也已改为调用仓库内统一计算脚本，并按原始交易文件修改时间处理重复订单。重复开卡订单的最新文件优先规则也已在正式 UPB 计算脚本中，并与仓库脚本一致。

## 结论与顺序

先保证数据可信、更新可验证和正式/测试隔离，再增加 KYB。无需现在重写整个网站或迁移全部历史交易到新数据库。

## 已确认的具体问题

### 1. 开卡张数可能重复（P0）

旧算法曾按文件分别统计，两个重叠导出里的同一成功付费订单可能算两次。现在 `load_card_data` 会按文件版本合并并按订单号全局去重；较新的状态/开卡费记录覆盖旧记录，单个文件内部若仍有冲突则停止。零开卡费卡号仍用于交易映射，但不计开卡张数。Desktop 正式脚本与仓库脚本一致；3 个回归测试已通过。线上张数需下次运行 UPB 全量命令重算。

### 2. 首屏可用性与快照日期（已修复，后续仍可优化）

正式实时接口已验收到 `2026-09-23`。后续复核又发现首屏内置快照也必须单独刷新，否则慢请求期间仍会暂时显示旧日期。UPB、UPW 两份备用 JSON 已从生产接口重新取得，最新日期均为 `2026-09-23`，并随正式 Worker 版本 `ccc4503a-bee7-45c3-aea9-fd67f3c08404` 发布。Chrome 已验证首页首屏显示 23 日、实时读取完成，以及切换到 Wallet 后也能显示 23 日数据。

后续应把手工随构建更新的静态快照改为同步程序发布的已验收快照，避免忘记重新打包；本地快照至少要持续显示真实截止日。

### 3. 多数据中心缓存与同步批次（后续优化）

`app/api/dashboard/route.ts` 正常读取缓存 600 秒；正式同步程序使用 `refresh=1` 绕过缓存并在上游成功后填充当前数据中心缓存。UPB、UPW 现在都从 `WALLET_SOURCE_URL` 指向的同一个 WalletSync 部署读取各自数据，避免 Business 继续命中旧的 Apps Script。

Cloudflare Cache API 按数据中心缓存，不会因某地刷新而自动复制到其他数据中心；冷数据中心仍可能需要约 47 秒重新计算 Apps Script。Worker 仍缺批次版本比较和共享存储，请求高峰时也缺少全局的刷新频率保护。参见 [Cloudflare Cache 文档](https://developers.cloudflare.com/workers/runtime-apis/cache/)。

建议把每批数据的 batchId、内容摘要、截止日期和总额一并发布到稳定存储；网页读取已验收版本，并拒绝较旧批次覆盖新批次。

### 4. 同步成功的判定过弱（P0）

现有 UPB 同步会比对本地与云端最新日，并比较刷新后网站与云端的完整 periods；网站验收失败返回非零码。仍未校验 batchId/行数/独立对账；写入后超时也没有状态查询接口，人工重跑前应确认 Sheet 是否已写入。

### 5. 写入没有原子性（P1）

`google-apps-script/WalletSync.gs` 的 `writeRows` 先清空再写，每张表依次更新；没有读写锁或版本切换。中途失败或两次同时运行，可能产生空表或新旧混合数据。staging 专用接口也有同类限制。

建议临时批次写入、完整校验后一次切换有效版本；保留最近成功版本。锁只能防并发，不能代替失败回滚或备份。增加恢复演练，而不仅是“有备份文件”。

### 6. 现有对账是恒等式，不能证明账算对（P1）

`build_business_history.py:617` 先以 `total_amount - shared_consumption` 得出充值模式金额，再将两项相加与 total 比较。差额自然接近零，即使上游漏单、归属错了，也可能显示通过。

应分别从去重后的充值订单、共享消费明细独立计算，再与日报、月报和网页结果对照；输出未匹配金额、冲突卡号数量、被过滤记录及原因。已有 `unmapped_clients.csv`、`source_coverage.csv`、`fx_rates_used.csv` 是很好的基础，但严重异常还需阻止发布。

### 7. “完整日期”不等于数据确实完整（P1）

`build_business_history.py:599` 只检查当月已出现渠道的最后交易日期。完全漏掉某渠道文件不一定触发错误；反过来，某渠道真实无交易也不应等于缺数据。充值、开卡与消费的覆盖日期也需要分别检查。

建议定义每个平台的必需文件/渠道清单，记录导出范围和完整性标记，区分“确认零交易”和“未收到文件”。统一业务时区和日切规则。

### 8. 目标与状态有未经明确配置的业务假设（P1）

UPW 与 UPB 都把月总目标平均分给公开 BD 加 UPay；这是当前算法，不代表实际考核规则。前端 `state` 把没有完成率也判为 Behind，且状态/关注列表使用固定 70%、43% 阈值，不看本月已过多少天。

建议总体目标与个人目标分别配置；无个人目标显示“未设目标”，不要虚构个人完成率。活跃状态依据有定义的时间窗与交易/开卡事件，不能仅凭净金额，因为消费与退款抵销时净额可能为零。进度状态应与时间进度比较。

### 9. 历史归属与合作模式会随当前配置重算（P1）

当前读取一张最新关系表应用到全部历史流水。BD 变更、充值/共享模式变更后，历史归属与总金额口径可能一起变化。需明确采用“交易当时关系”还是“当前关系追溯重算”；若保留历史，加入生效起止日期及稳定客户ID。

前端 Wallet 公开 BD 名单又硬编码一份（`app/page.tsx:51`），可能把配置表中新加入的 BD 再归入 UPay。应由一个经过校验的数据契约提供公开名称，不在前后端维护两份名单。

### 10. 汇率需要过期与币种检查（P1）

现有程序已使用 FRED 历史汇率并记录来源/匹配日期，这是优点。但下载失败后可以继续用缓存，并向前匹配且没有最大陈旧期限。Passto 按渠道统一换算，没有把读取的币种字段作为校验条件。

建议校验正汇率、输入币种、汇率日期距离及缺失天数；周末沿用与异常陈旧缓存分开处理。明确使用参考日汇率而非实际结算汇率，并保留原币、原额、汇率及 USD 结果。不要把这个看板当作财务账。

## 工程、操作和产品上的缺口

- **版本一致性：** 正式桌面启动器调用独立数据目录，网站由仓库 Worker 部署。已确认 UPB `build_business_history.py` 与仓库副本一致，但其他脚本/依赖仍需逐项比较。建议逐步统一代码来源、显示数据批次/计算版本并保留发布记录。
- **安全：** 当前页面与 API 代码未见应用级鉴权。真实业务看板应限制授权人员访问；保护页面和 API 两端，不能仅隐藏菜单。用户已明确决定 staging 公开并接受真实运营汇总数据可被任何访问者看到；这属于接受风险的例外，不代表原始订单/卡号明细或密钥可以公开。同步读写密钥应分权、避免放在浏览器，日志应脱敏。
- **运维：** 当前错误大多被吞掉。建议监控数据是否按时更新、同步失败、接口耗时/错误率、源站请求数、流量及费用；不仅监控网站是否返回 200。Cloudflare 支持指标、日志及跟踪：[官方说明](https://developers.cloudflare.com/workers/observability/)。未进行生产压测，因此不承诺具体并发人数。
- **使用流程：** 一个入口显示正在处理哪个平台/环境、文件覆盖区间、异常数量和本批发布结果；保留详细日志供排查。程序检查依赖版本与目录；避免用户凭终端警告判断成败。
- **自动化测试：** 现有回归测试覆盖开卡去重与部分同步/环境保护，但仍未覆盖所有业务口径。需继续覆盖免费卡参与交易、手动卡匹配、共享/充值模式、退款、跨月目标、关系变更、缺渠道和环境误配。
- **前端维护：** `app/page.tsx` 把指标算法、请求、筛选和图表挤在一个组件内，许多逻辑为超长单行。建议拆分纯计算函数、数据请求层和图表/表格组件，统一日期控件、排版与错误状态；增加键盘操作及小屏检查。
- **指标名称：** “Projected gap”实际是目标减已完成，并非预测；“vs previous day”显示的是最新一天金额，没有计算日环比；周期天数/日均用有记录的报告天数，可能不同于日历天数。需让名称与算法一致。
- **导出：** 当前按钮调用 `window.print()`，不是结构化数据导出。若业务需要，应增加与当前筛选一致的 CSV/XLSX、统计口径与免责声明。
- **性能：** 两个生产备用 JSON 原文件合计约 4.5 MB；这不是实际压缩传输量，但表明历史数据被整体导入。先测实际包体/接口体积，再按平台和月份加载，累计趋势用线性累加，避免每天重复 slice/reduce。不建议为此立即重写框架。
- **环境同构：** 测试与正式要使用同一版计算逻辑、不同资源和配置；独立测试 Apps Script 目前是另一个实现，后续需收敛成共用源码及配置生成，避免“测试通过但正式逻辑不同”。

## KYB 上线前必须补齐

先设计人员角色（提交人、BD、审核人、管理员）、数据可见范围、材料版本、审批状态及状态转换、退回/补件、操作日志、通知和附件访问。敏感附件应放私有存储，通过短期授权访问，不能放公开网站静态目录或公开测试数据表。测试只使用虚构材料。审批决定不应交给看板自动评分代替人工授权。

在进入多用户审批、状态变更与附件管理时，再评估专用数据库及私有对象存储；当前看板可先保留 Google Sheets 作为运营录入工具。数据库、文件、账号、通知渠道也应按环境隔离。保留期限和合规要求需由业务/法务另行确认。

## 建议实施批次

1. 完成 staging 端到端验收与防误写；确认本地、桌面程序、线上版本一致，并明确 staging 是否使用当前生产实时数据源。
2. 保持开卡去重和新快照在下次真实批次中的回归；补独立对账及阻断规则。
3. 确认个人目标、历史归属和退款/活跃口径，再修指标与状态。
4. 加权限、告警、恢复流程和自动化发布检查，然后做 UI/性能优化。
5. 最后单独立项 KYB。以上审查建议并不意味着已自动在生产实施。
